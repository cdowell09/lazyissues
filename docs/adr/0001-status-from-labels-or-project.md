# Status comes from labels or a project, chosen per repository

GitHub issues only have open and closed states, so a workflow position needs to be stored somewhere else. Each repository in the repo set has one status source: either status labels, or the Status field of one GitHub Project. Statuses are names the user defines, in an order the user chooses, with no built-in list, and a label or project option counts as that status when the names match, ignoring case and treating `-`, `_` and spaces alike. So `in-progress` in one repo and "In Progress" on another repo's project form one group. We rejected deciding per issue (use the project's Status if the issue is on the project, otherwise its labels) because an issue could then carry two statuses that disagree. Done always means closed, and the close reason (completed, not planned, duplicate) takes the place of Jira's resolution. A project's done options are reached by closing, since GitHub's built-in project workflow sets them on close. Neither source enforces a workflow, so any status can move to any other, and lazyjira's transitions have no equivalent here.
